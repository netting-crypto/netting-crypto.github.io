# Roomie 产品需求与功能规格（考试版）

> 版本：V1.0 Requirement Freeze  
> 项目：Roomie — 合租生活管家 / Spatial Home Manager  
> 目标：用于 Vibe Coding / 产品设计考试原型，强调「空间化提醒 + 多人共同生活协作 + 事件闭环」  
> 核心体验：**家里发生什么，就在它发生的位置出现；人与人之间需要共同确认的事情，则进入白板或记账本。**

---

# 0. 一句话定义

**Roomie 是一个把合租中的公共事务映射回真实居住空间，并持续记录“谁发现、谁负责、谁完成、最后如何闭环”的共同生活系统。**

它不是四张表的集合，也不是普通 Todo List。

它要回答三个问题：

1. **这个家哪里有事情发生？** → 3D Home
2. **现在轮到我做什么？** → My Roomie 左侧待办
3. **我们之间还有什么需要共同确认？** → 白板 + 记账本

产品原则：

> **人发现 / 时间到达 → Roomie 记录并组织 → 把需要行动的人叫过来 → 人完成 → 家的状态发生变化并留下记忆。**

---

# 1. 目标用户与使用场景

## 1.1 目标用户

2–5 人长期合租的年轻用户，典型问题包括：

- 公共费用谁垫了、谁还没付，需要反复催。
- 水、电、网费、房租等周期账单容易忘。
- 公共用品缺了以后没人补，或者买了以后忘记 AA。
- 厨房、卫生间、客厅等公共区域值日不明确。
- 室友共同规则散落在聊天记录里，没有确认过程。
- 谁承担了哪些公共事务缺少记录，时间久了容易形成“我是不是一直在做”的模糊矛盾。

## 1.2 考试版假设

本版本不假设存在智能家居传感器，也不假设系统可以自动知道卫生纸还剩多少。

系统只允许三种合法的信息来源：

1. **人主动发起**：例如“卫生纸快没了”“我刚买了垃圾袋”“我们刚吃完饭，需要 AA”“我想发起一条新规则”。
2. **时间 / 周期触发**：例如“今天轮到你打扫厨房”“每月 1 日房租到期”“本月电费该录入了”。
3. **前序动作衍生**：例如“购买卫生纸 → 自动生成 AA”“修改规则 → 其他室友需要重新确认”。

禁止在 Demo 中表现为“Roomie 神奇地知道现实世界发生了什么”。

# 2. 核心产品原则

## 2.1 空间优先

有稳定空间归属的事情，应尽可能挂在真实空间或物件上，而不是先进入表格。

例：

- 卫生纸不足 → 卫生间纸巾架
- 垃圾桶满 → 厨房垃圾桶
- 厨房值日 → 厨房地面 / 清洁工具
- 洗衣液需要补充 → 阳台洗衣区

## 2.2 共同事务与空间事务分开

### 空间事务 Spatial Matters

有明确、稳定的房间 / 物件归属。

典型类型：

- 清洁
- 补货
- 公共物品
- 维护 / 故障（可扩展）

### 共同事务 Shared Matters

需要多人确认、付款或讨论，但没有稳定空间归属。

由两个明确入口承载：

- **白板**：规则、提案、讨论
- **记账本**：房租、水电网费、临时 AA、采购 AA

## 2.3 同一事件，多视角呈现

同一个事件可以同时出现在：

- 3D Home：显示发生位置
- My Roomie：显示“我需要做什么”
- 白板 / 记账本：显示共同状态
- History：显示过去发生过什么

这些不是四套独立数据，而是同一事件的不同视图。

## 2.4 完成必须改变环境

Roomie 的关键区别不是“3D 好看”，而是：

> **系统状态改变以后，空间也应该发生变化。**

例如：

- 清洁完成 → 地上的纸团消失
- 垃圾倒掉 → 垃圾桶恢复为空
- 卫生纸补充 → 缺货标记消失 / 物件恢复正常
- 房租 3/3 收齐 → 记账本显示已结清 + 轻庆祝动画
- 规则 3/3 确认 → 草案便利贴移动到“已生效”区域

# 3. 用户与权限

考试版默认 3 位室友：

- **You**
- **小王**
- **小李**

禁止出现开发者真实姓名。

## 3.1 权限原则

考试版不做复杂隐私 / 角色权限。

默认：

- 所有人都能查看全部公共事务。
- 创建人可以编辑 / 撤回自己创建但尚未完成的事项。
- 规则需要全部参与者确认后才进入“已生效”。
- 账单每个人只确认 / 支付自己的份额。
- 公共任务允许未指定责任人时被任意室友认领。

# 5. 核心数据对象

## 5.1 House

字段：

- `house_id`
- `members[]`
- `rooms[]`
- `recurring_rules[]`

## 5.2 Room

示例：

- Living Room
- Kitchen
- Bathroom
- Balcony / Laundry
- Bedroom A / B / C

字段：

- `room_id`
- `name`
- `anchors[]`
- `health_state`

## 5.3 Anchor（空间锚点）

代表一个事项可以附着的位置。

示例：

- `bathroom.toilet_paper_holder`
- `kitchen.trash_bin`
- `kitchen.floor`
- `balcony.detergent_area`
- `living.whiteboard`
- `living.ledger`

新建的用户物品可以映射到已有 Anchor，不要求生成真实 3D 模型。

## 5.4 Item（公共物品）

示例：卫生纸、垃圾袋、洗衣液。

字段：

- `item_id`
- `name`
- `category`
- `room_id`
- `anchor_id`
- `icon`
- `last_event_at`

注意：考试版**不维护虚假的实时库存数值**。如果没有真实传感器 / 用户持续记账，不展示“系统精确知道还剩 17%”。

可以展示用户主动报告的语义状态：

- 正常
- 快没了（用户报告）
- 已用完（用户报告）
- 已补充

## 5.5 Task（空间任务）

字段：

- `task_id`
- `type`: cleaning / restock / maintenance / custom
- `source`: human / recurring / derived
- `room_id`
- `anchor_id`
- `assignee`
- `due_at`
- `status`
- `created_by`

任务状态不强制所有类型共用同一状态链。

临时补货任务常见：

- `unclaimed`
- `claimed`
- `resolved`

周期清洁常见：

- `pending`
- `overdue`
- `completed`

## 5.6 Expense（公共支出）

来源分两类：

### Recurring Expense 周期支出

房租、水、电、网费等。

### Ad-hoc Expense 临时支出

卫生纸、聚餐、临时公共采购等。

字段：

- `expense_id`
- `title`
- `type`
- `payer`
- `amount`
- `participants[]`
- `split_method`
- `source_event`
- `status`

状态：

- `pending_confirmation`（可选）
- `pending_payment`
- `settled`

考试版为了简化，可直接使用：

- 待支付
- 已结清

## 5.7 Split（个人分摊）

字段：

- `expense_id`
- `member_id`
- `amount`
- `payment_status`

状态：

- 待支付
- 已支付
- 垫付人

## 5.8 Rule / Proposal（共同规则）

字段：

- `rule_id`
- `content`
- `creator`
- `status`
- `agreements[]`
- `comments[]`
- `version`

状态：

- 草案
- 讨论中
- 待确认
- 已生效

## 5.9 Action（个人待办）

这是 My Roomie 的统一对象。

无论来源是清洁、账单还是规则，最终都可以产生 Action。

字段：

- `action_id`
- `member_id`
- `type`
- `source_type`
- `source_id`
- `title`
- `due_at`
- `status`
- `room_id`（可为空）
- `anchor_id`（可为空）

## 5.10 History Event（历史动作）

每个关键动作都记录。

示例：

- 某人报告卫生纸快没了
- 某人认领采购
- 某人完成购买
- 系统生成 AA
- 某人完成支付
- 全员结清
- 某人发起规则
- 某人留言讨论
- 某人同意规则
- 规则正式生效
- 某人完成值日

# 6. 事件来源模型

所有事情必须明确属于以下三种来源之一。

## 6.1 Human Trigger — 人主动发起

场景：

- 我发现卫生纸快没了
- 我刚买了卫生纸
- 我们刚吃完饭，需要 AA
- 我发现灯坏了
- 我想提出一条共同规则

## 6.2 Time / Recurring Trigger — 时间触发

场景：

- 今天轮到你打扫厨房
- 每月 1 日房租生成
- 每月 10 日提醒录入电费

## 6.3 Derived Trigger — 前序动作衍生

场景：

- 购买卫生纸 → 自动生成采购 AA
- 新规则 → 其他室友产生“待确认” Action
- 修改规则 → 所有人重新确认
- 账单生成 → 参与者产生支付 Action

# 7. 功能需求总表

## 7.1 3D Home

| 项目 | 需求 |
|---|---|
| 核心目的 | 用空间状态告诉用户“哪里有事” |
| 默认视图 | 等距 / dollhouse 风格 3D 公寓 |
| 操作 | 拖动旋转、滚轮缩放、点击热点 |
| 墙体 | 智能 cutaway：挡视线的前墙降成矮墙，背墙保留 |
| 房间 | 客厅、厨房、卫生间、阳台 / 洗衣区、卧室 |
| 任务表达 | 物件 / 区域旁出现 `!` |
| 完成表达 | `! → ✓`，同时环境改变 |
| 点击结果 | 镜头聚焦对应位置 + 打开任务面板 |
| 自定义物品 | 未有 3D 模型时用通用 icon / pin 代替 |

### 3D 必须存在的核心锚点

客厅：

- 白板 → 规则与讨论
- 记账本 → 账单与 AA
- 地面 → 客厅清洁

厨房：

- 垃圾桶 → 倒垃圾
- 地面 / 清洁工具 → 厨房值日
- 冰箱 → 公共物品 / 食材入口（P1）

卫生间：

- 卫生纸 → 补货
- 垃圾桶 → 倒垃圾
- 洗手台 → 清洁（P1）

阳台：

- 洗衣机 → 公共设备状态（P1）
- 洗衣液 → 补货

## 7.2 My Roomie — 左侧个人待办栏

### 核心目的

回答：**今天和我有关的事情是什么？**

### 信息结构

默认显示：

- 待我处理
- 等待别人
- 已完成（折叠）

任务类型可以混合：

- 房租待支付 ¥2,500
- 卫生纸采购已认领
- 今晚厨房值日
- 新规则待确认

筛选：

- 全部
- 钱
- 值日
- 物品
- 规则

### 行为

点击任务：

- 有空间锚点 → 镜头跳到对应空间
- 账单 → 打开记账本对应账目
- 规则 → 打开白板对应便利贴

逾期：

- 文案 + 红色状态强调
- 支持室友“戳一戳”

---

## 7.3 白板 Whiteboard

### 核心目的

负责**共同规则、提案与讨论**，不承载账单。

### 视觉形式

点击客厅白板后，进入以白板为背景的大面板 / 全屏 Overlay。

区域：

1. 待表决
2. 讨论中
3. 已生效

### 卡片示例

> 访客留宿需要提前一天通知  
> 2 / 3 已同意  
> [同意] [继续讨论]

### 讨论

点击“继续讨论”：

- 展开留言区
- 用户可以追加评论
- 产生 History Event
- 所有相关成员产生“规则待查看 / 待确认” Action

### 状态

草案 → 讨论中 → 待确认 → 已生效

规则内容被修改后：

- `version + 1`
- 原确认失效
- 重新进入待确认

### 完成动画

3 / 3 同意后：

- 草案便利贴移动到“已生效规则”区域
- 出现轻量 ✓ / sparkle

---

## 7.4 记账本 Ledger

### 核心目的

统一承载所有“钱”的事情。

类型：

- 房租
- 水费
- 电费
- 网费
- 公共采购 AA
- 聚餐 / 临时 AA

### 视觉形式

点击客厅记账本后，打开“摊开的账本”式界面。

建议双栏：

左侧：本期待结算  
右侧：最近账目 / 历史

### 周期账单

#### 房租

首次设置：

- 周期：每月 1 日
- 固定金额：¥7,500
- 分摊方式：3 人均分

之后系统自动生成每月账单。

#### 水 / 电 / 网费

如果金额不固定：

系统只能生成：

> “本月电费该录入了”

经办人输入实际金额后，才产生 Split。

### 临时 AA

场景：

- 聚餐后回来录入
- 公共用品已经购买后录入

创建字段：

- 标题
- 总额
- 垫付人
- 参与人
- 均摊 / 自定义金额

提交后：

- 参与者产生支付 Action
- 记账本显示支付进度

### 支付

考试版不做真实支付接入。

可展示概念性：

- `去支付`
- 弹出模拟二维码
- 微信 / 支付宝字样
- `模拟支付成功`

支付完成：

- 对应 Split → 已支付
- 3 / 3 后 Expense → 已结清
- 触发庆祝动画

---

## 7.5 公共物品 / 补货

### 核心原则

Roomie 不自动猜库存。

用户需要主动报告。

### 入口 A：点击已有物品

例如点击卫生纸：

> 发生什么了？

选项：

- 快没了
- 已经没了
- 我刚买了新的

#### 快没了 / 已经没了

下一步：

- `我来处理`
- `告诉室友`

如果“告诉室友”：

- 生成未认领 Task
- 物件旁出现 `!`
- 其他室友可点击“我来买”

如果“我来处理”：

- Task 直接 assigned to You

#### 我刚买了新的

填写：

- 金额
- 是否公共支出
- 参与人

提交：

- Item 恢复正常
- 自动生成采购 Expense / AA

### 入口 B：全局 Add

允许创建原本不存在的 Item。

字段：

- 名称
- 类别
- 房间
- 锚点 / 区域
- 图标

如果下拉没有该物品：

> `+ 创建新物品`

系统不生成新的 3D 模型，而是：

- 按类别映射通用 icon
- 在指定 Anchor 旁生成小 pin / icon

示例类别：

- 清洁用品 → bottle icon
- 食品 → food icon
- 日用品 → box icon
- 家电 → appliance icon
- 其他 → 通用 icon

---

## 7.6 清洁 / 排班

### 核心原则

清洁适合系统自动生成，因为它有明确周期，不需要 Roomie 判断“现在到底脏不脏”。

### 示例

每周日：厨房值日

系统到期时：

- 生成 Action
- 指定责任人
- 厨房地面出现纸团 / 垃圾状态
- `!` 出现

### 状态

- 待完成
- 已逾期
- 已完成

### 操作

- `我已完成`
- `申请换班`（P1）

### 完成效果

- 地面纸团消失
- 垃圾桶恢复正常
- `! → ✓`
- 小型 sparkle / confetti
- 写入 History

### 排班视图

考试版不做复杂甘特图。

优先使用轻量 Weekly Timeline：

```text
SUN 13
厨房       小王
倒垃圾     You

MON 14
卫生间     小李

TUE 15
客厅       小王
网费       自动生成
```

## 7.7 全局 Add

### 固定入口

右下角 `+ Add`，不能依赖用户在 3D 中探索。

### 一级入口

1. 空间事项
2. 公共支出
3. 共同提案

### 空间事项

字段：

- 房间
- 物品 / 区域
- 事项类型
- 是否自己处理
- 是否公开待认领
- 截止时间（可选）

### 公共支出

跳转记账本创建账单。

### 共同提案

跳转白板创建规则 / 讨论。

# 8. 通知与提醒机制

## 8.1 系统提醒是主机制

默认不要求人手动催。

系统提醒来源：

### 状态 / 人为报告

有人报告：

> 卫生纸快没了

### 时间

> 今天轮到你打扫厨房

### 协作动作

> 新规则需要你确认  
> 火锅 AA ¥92 待支付

提醒在：

- My Roomie 左侧待办
- 对应 3D Anchor 的 `!`
- 白板 / 记账本的待处理标记

## 8.2 “戳一戳” Poke — 社交催办亮点

不是主提醒机制，而是逾期 / 久未处理后的轻量社交催促。

### 触发位置

逾期 Action / 未支付账单 / 未确认规则旁：

> `戳一戳`

### 动画

要求轻量实现：

1. 全屏轻微暗化
2. 一个巨大的手指从一侧进入
3. 手指向目标方向左右 / 前后快速戳两下
4. 屏幕轻微 shake
5. 出现巨大 `!`
6. 文案出现

示例：

> 有人戳了戳你  
> 厨房值日还没完成

按钮：

- `我已完成`（适用于清洁）
- `去处理`
- `知道了`

### 行为

`去处理`：直接导航至对应对象。

### 冷却

# 19. 产品主张（答辩可用）

Roomie 最核心的创新不是“做了一个 3D 网页”，而是改变了合租事务的组织方式：

传统合租管理通常把账单、清洁、物资、公约拆成几张表；Roomie 则把**有空间归属的事务重新挂回真实居住空间，把需要多人共识的事务放到白板和账本，再用个人待办把所有需要“我行动”的事情统一起来。**

因此整个产品的逻辑可以浓缩为：

> **发生在哪里，就在哪里被看见；需要谁行动，就出现在谁的 My Roomie；需要大家达成共识，就进入白板或账本；事情处理完成后，这个家本身也会恢复状态并留下记忆。**
